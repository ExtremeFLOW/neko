bool hip_have_mfma ( )
inlinestatic

Returns true if the current device exposes the matrix cores used by the MFMA strategies (currently gfx90a / MI250X and gfx942 / MI300A / MI300X) and this build actually compiled the device code for them. The f64 4x4x4 / 16x16x4 and f32 16x16x4 instructions are all available on these arches, so a single check gates either precision. Result is cached after the first query.

◆ hip_mfma_arch_probe()

__global__ void hip_mfma_arch_probe ( int * flag)
static

Shared matrix-core (MFMA) primitives for the spectral-element tensor contractions, used by the Ax-helm autotuner strategy.

Shared by every operator that offers a matrix core strategy: the scalar, vector and compressible Ax-helm, dudxyz, opgrad, conv1 and cdtp. The contraction primitives below are the hardware-validated versions – see the layout note on mfma_contract_4x4 for why they must not be re-derived from host simulation alone – plus one, mfma_contract_4x4x1, whose layout is documented rather than measured and which the tuner verifies at runtime before it is allowed to win, see the note there.

Maps a reference derivative-matrix * field contraction onto the AMD matrix cores on CDNA2 (MI250X / gfx90a) and CDNA3 (MI300A / MI300X / gfx942). Each precision has two tiles, which every operator's autotuner measures against each other (TILE, see NEKO_MFMA_TILE below):

f64 TILE 0 v_mfma_f64_4x4x4f64 batched, four blocks, mfma_contract_4x4 f64 TILE 1 v_mfma_f64_16x16x4f64 mfma_contract f32 TILE 0 v_mfma_f32_4x4x1f32 batched, sixteen blocks, elements batched too, mfma_contract_4x4x1 f32 TILE 1 v_mfma_f32_16x16x4f32 mfma_contract

-DMFMA_F64_USE_16X16 and -DMFMA_F32_USE_16X16 collapse a precision onto its 16x16x4 tile. One thread block is launched as NWF 64-lane wavefronts (blockDim = (64, NWF, 1)) covering EB elements; each contraction is a D * U GEMM with M = LX, N = LX^2, K = LX, the partial tiles masked off, and the f32 4x4x1 tile batches NEL elements into one instruction stream at low order, see NEKO_MFMA_NEL_N.

Supported for 4 <= LX <= 12 in double precision and 2 <= LX <= 12 in single; the upper bound is set by the LDS needed to keep the cubes resident (operators stage four cubes plus three LX^2 derivative matrices, 63360 B of f64 at LX = 12 with the padded Ax-helm layout, 58752 B without it), the lower one by what a tile can still fill, see mfma_lx_supported().

16x16x4 register/lane layout (used by the f32 tile and the f64 16x16x4 fallback; the 4x4x4 layout is documented at mfma_contract_4x4).

Verification status, since this tile came from the same source that got the 4x4x4 block selector and contraction index the wrong way round: CONFIRMED on gfx90a 2026-08-22, both accumulator packings. The f32 sweep of mfma_probe covers the A and B layouts (shared between precisions) and the i = 4*g + r packing at ~1e-7, fp32 epsilon; a second run with -DMFMA_F64_USE_16X16 covers the i = g + 4*r packing at ~1e-16. A layout error reads as O(1) here, so neither pass rests on a loose tolerance.

Note the f64 results are bit-identical between this tile and the 4x4x4 one. That is expected rather than suspicious: both decompose K into chunks of four with one MFMA per chunk accumulated in sequence, so the summation order is the same. It is not the signature of dead code, which is what identical results across NWF would be – NWF changes which wavefront takes which column group and so must perturb the schedule. D = A*B + C, wave of 64 lanes, g = lane/16 in 0..3, c = lane%16 in 0..15. A and B share the same layout for both precisions; only the accumulator packing of the 16x16 result differs: A[i][k] : lane holds A[i = c][k = g] B[k][j] : lane holds B[k = g][j = c] D[i][j] : lane holds D[j = c] in accumulator slot r = 0..3, with row i = g + 4*r for f64 (rows spread with stride 4) and i = 4*g + r for f32 (four contiguous rows per lane group)

◆ mfma_lx_supported()

template<const int LX>
bool mfma_lx_supported ( )
inlinestatic

Compile-time predicate for the LX values that the MFMA strategy supports. Double precision 4 <= LX <= 12, single precision 2 <= LX <= 12, bounded above by the LDS needed to keep one element resident. MUST match the dispatch specialisations in each operator's kernel header.

Both precisions are verified against a reference on gfx90a (mfma_probe, 144 configurations, 2026-08-22) on the 16x16x4 tile and, in double precision, on the 4x4x4 one. The single precision lower bound is 2 because the batched 4x4x1 tile makes those orders worth having – sixteen lx = 2 elements or four lx = 4 elements to one instruction, and p-multigrid smooths at both – where the 16x16x4 tile would be 2% and 25% utilised. Double precision keeps 4: its 4x4x4 tile already fills M there and batches nothing across elements, so lx = 2 would be a 6% utilised instruction. The tuner's verification pass (NEKO_TUNE_VERIFY, elem_block_tune.h) rejects any candidate that does not reproduce the reference formulation, so an order or tile that is wrong on some part fails loudly at tuning rather than silently in the solve.
